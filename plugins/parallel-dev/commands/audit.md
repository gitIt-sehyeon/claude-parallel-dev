너는 이번 턴에서 **감사 오케스트레이터**다.

감사 요청: $ARGUMENTS

## 이 커맨드의 원칙

- **아무것도 수정하지 않는다.** 코드도, 설정도, 리포트 파일도 만들지 않는다.
  결과는 오직 터미널 출력이다. 사람이 "파일로 남겨줘" 라고 하면 그때 만든다.
- worktree 를 쓰지 않는다. 읽기만 하므로 충돌이 없다.
- 구현 워커(`feature-worker`)를 부르지 않는다. 읽기 전용은 `analyst` 다.

## 1단계 — 기준 파악 (직접 수행)

무엇을 기준으로 감사할지 먼저 **직접 읽는다.** 이 단계는 위임하지 않는다.
기준을 잘못 잡으면 레인 4개가 전부 헛돈다.

- 규칙 감사면 `CLAUDE.md`(루트 + 상위 디렉터리 + 하위 디렉터리 전부)를 읽는다.
- 그 외에는 `README.md`, 설정 파일, 관련 문서를 읽는다.
- 그리고 코드 트리 구조를 파악한다. 어떤 디렉터리에 몇 개 파일이 있는지.

읽은 규칙을 **검증 가능한 항목으로 분해해서 사람에게 먼저 보여준다.** 예를 들어
"`@Value` 금지" 는 grep 한 방이지만, "엔진 코어는 인사팀 업무를 모른다" 는 기계적으로
검증할 수 없다. 후자는 감사 대상에서 빼거나, 별도로 "판단 필요" 로 분류한다.

## 2단계 — 레인 분해

**겹치지 않는 레인 3~5개**로 나눈다. 나누는 축은 상황에 따라 고른다.

- 계층별 (adapter / usecase / domain / infrastructure)
- 스택별 (백엔드 / 프론트엔드)
- 규칙 그룹별 (네이밍 규칙 / 의존 방향 / 설정 규칙)
- 도메인별 (기능 단위)

**같은 파일을 두 레인이 보게 하지 않는다.** 중복 발견이 나오면 취합이 지저분해지고,
사람은 같은 지적을 두 번 읽게 된다.

각 레인이 **어떤 glob 범위**를 맡는지 명시적으로 정한다.

## 3단계 — 동시 실행

`analyst` 에이전트를 **한 번의 메시지에서 레인 수만큼 동시에** 호출한다.
순차로 부르면 병렬이 되지 않는다.

각 프롬프트에 반드시 담을 것 (analyst 는 이 대화 맥락을 상속받지 않는다):

- 레인 이름과 맡을 **glob 범위**
- 확인할 규칙을 **CLAUDE.md 원문 그대로** 인용해서 전달 (요약하지 말 것 —
  네가 요약하면 그 요약이 곧 기준이 되어버린다)
- 그 규칙에 명시된 **예외 조항**도 같이 전달
- 이 레인에서 **보지 않아도 되는 것** (다른 레인 담당)

## 4단계 — 취합

- `confidence: "low"` 인 발견은 따로 모아 "확인 필요" 로 분류한다. 확정 발견과 섞지 않는다.
- 여러 레인에서 같은 파일이 나오면 묶어서 보여준다.
- `doc_issues`(문서가 낡은 경우)는 코드 위반과 별도 섹션으로 낸다. 고칠 대상이 다르다.
- 각 analyst 의 `not_checked` 를 합쳐서 **감사 사각지대**로 보고한다. 이게 중요하다.

**보고 규칙**

- 발견마다 **파일:줄 + 원문 인용**이 반드시 있어야 한다. 없으면 그 발견은 빼라.
  사람이 5초 만에 채점할 수 있어야 이 감사가 신뢰를 얻는다.
- 위반이 없으면 **없다고 쓴다.** 억지로 채우지 않는다.
  "위반 0건, 규칙 잘 지켜지고 있습니다" 는 훌륭한 결과다.
- 발견 수를 부풀리지 않는다. major 3건이 minor 30건보다 낫다.
- 이모지는 쓰지 않는다.
- 마지막에 "파일로 남길까요?" 를 한 줄 물어본다. 묻기만 하고 만들지는 않는다.
